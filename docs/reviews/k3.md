## Code Review: intercom-supervisor extension (full-project review)

### Summary
Two pi sessions pair over the pi-intercom channel: a worker publishes a compacted "view" on every `agent_settled`, and a supervisor steers it via directives until the human stops the loop. The wire protocol, validation, and view construction are careful and well-tested. The weak spot is liveness: the pairing handshake is fire-and-forget, and several transitions silently abandon a partner, leaving the other side in a state it can never exit on its own.

### Critical (must fix)
- **src/index.ts:60-65, 178-180 — a refused or lost `pair` leaves both sessions stuck forever.** The worker drops a `pair` when `state.role !== "none"` and says nothing back. The supervisor, meanwhile, has already committed `role: "supervisor"` and waits for a view that will never arrive — views from that worker go to whoever it is actually paired with, and this supervisor's steers are dropped as unpaired. Realistic scenarios: (1) the worker's previous supervisor crashed or was closed without `done`/`unpair` — the worker is now permanently bound to a dead session ID and silently rejects every future pair; (2) two supervisors race, the loser never learns it lost; (3) the target session doesn't have this extension loaded (`listSessions` doesn't filter on capability, so `/supervise <name>` can target a session that will never respond). In all cases the supervisor tells the human it is "watching" and nothing ever happens again, on both sides. Fix: add a pair acknowledgment (worker replies `paired`/`busy`); on `busy` or no-ack-within-timeout, reset the supervisor to `none` and notify the human. At minimum, `/supervise stop` documentation should cover the worker side, since that is currently the only recovery.

### Important (should fix)
- **src/index.ts:149-158 — `/supervise` overwrites an existing pairing without unpairing the old partner.** Run while `role === "worker"` (this session is being supervised) or while already supervising someone else, and the old partner is abandoned: its directives/views are dropped as unpaired and it sits in the stuck state above. Fix: refuse when `state.role !== "none"` (tell the user to `/supervise stop` first), or send `unpair` to the current `pairedId` before re-pairing.
- **src/index.ts:53, 91-93, 151 — `latestView` survives state resets and re-pairings.** It is only overwritten when a `view` arrives. After `done`/`unpair`/`stop` and a fresh `/supervise` to a *different* worker, `worker_view` returns the previous worker's view, and `done`'s outstanding-work guard (`latestView.match(...)`) judges the old worker's state. Fix: set `latestView = ""` everywhere `state` is reset to `EMPTY_STATE` and when a new pairing is initiated.
- **src/index.ts:220-224 — the goal never propagates to the worker after pairing.** The worker's view header renders `state.goal` captured at `pair` time; the supervisor's `set_goal` (the designed path for "no goal given") updates only the supervisor's state. Every subsequent view keeps showing `# Goal: not set`, and the supervisor LLM is asked to judge progress against a goal the view claims doesn't exist. Fix: include the current goal in `directive` (and refresh worker state on receipt), or add a `goal` wire message sent by `set_goal`.
- **src/index.ts:131-137 — `agent_settled` rethrows from a fire-and-forget handler.** The `catch` logs and rethrows, producing an unhandled rejection with no user notice — the exact failure mode the `onEvent` wrapper (index.ts:100-106) was written to avoid. A view that fails to publish means the supervisor never wakes and the loop stalls silently. Fix: mirror the `onEvent` handling — notify via `ctx.ui.notify` and swallow, or retry.

### Suggestions
- **src/index.ts:79 — `pi.sendUserMessage(REVIEW_NUDGE(...))` with no delivery options.** If the supervisor is mid-turn when a view arrives, this queues as a follow-up; two rapid worker settles could stack nudges referencing stale `steerRounds`. Harmless in practice, but worth a comment since the directive path deliberately chose `steer` semantics for the symmetric case.
- **src/protocol.ts:67-72 — one `STATE_ENTRY` appended per steer.** Over a multi-day uncapped run (the stated design), session files accumulate one entry per steer round. Consider replacing rather than appending, if the entry API allows.
- **src/view.ts:81 — the exit-code regex can false-positive on content** (e.g. a `read` of a log file containing "exited with code 1" from an unrelated process). It's a heuristic and errs toward caution, so acceptable — a comment saying so would help.
- **src/prompts.ts:47 — "This is review ${rounds + 1}"** counts steers, not reviews; after a `set_goal` or a plain-text reply the number no longer matches view count. Cosmetic, but the supervisor LLM may read meaning into it.

### Positive
- src/index.ts:68-73 — the steer-vs-idle delivery choice (interrupt a busy worker, start a turn on an idle one) is the right call and is regression-tested against the real failure that motivated it.
- src/index.ts:212-218 + src/view.ts:76-89 — refusing `done` while tool calls lack results closes a genuine false-completion hole.
- src/index.test.ts:163-176 — building the view from `getBranch()` rather than `getEntries()`, with a test that separates the two, catches a subtle rewind/fork bug class.

### Verdict
REQUEST CHANGES

The core loop is sound, but the pairing handshake needs an acknowledgment (or at least refusal detection) before this is safe to leave running unsupervised — right now the most likely real-world failure (dead partner, refused pair, wrong target) is indistinguishable from normal operation, on both sides.
